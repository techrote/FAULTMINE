# FAULTMINE deterministic headless batch-mining contract

Status: FM-014 batch/descriptors/diversity contract v1.

## Purpose and authority boundary

FM-014 exposes the accepted deterministic mutation/render/export stack as a headless search instrument. It does not define a second rendering engine, a second mutation algorithm, or a subjective aesthetic scorer.

`FAULTMINE-batch.exe` uses:

- the ordinary default `FaultRegistry` and FM-009 `generate_descendant` mutation policy;
- the ordinary `render_pipeline_at_frame` CPU canonical renderer;
- FM-004 deterministic nearest-neighbour proxy preprocessing only when an explicit proxy render mode is requested;
- FM-010 lineage/project semantics for GUI-importable mined specimens;
- FM-012 contact-sheet/still exporters for selected canonical outputs.

A batch result is therefore a deterministic search over explicitly addressed descendants. Thread scheduling, completion order and resume boundaries are performance concerns rather than semantic inputs.

## Batch address v1

A batch request identifies one finite half-open descendant range `[index_begin,index_end_exclusive)` plus:

- normalized full-source identity;
- complete parent canonical genome and identity;
- explicit mutation seed;
- FM-009 mutation radius and active mutation locks;
- mutation policy version;
- explicit semantic frame index;
- render mode: `canonical` or explicit deterministic `proxy`;
- proxy specification when relevant;
- visual descriptor version;
- inclusive near-duplicate descriptor-distance threshold;
- requested diversity-selection count.

Candidate `N` is always generated by the accepted FM-009 descendant address using that explicit descendant index. No batch-global PRNG sequence exists. A deterministic candidate identity is SHA-256 over a domain-separated textual address containing source identity, parent identity, mutation seed/radius, descendant index, frame, render mode/proxy specification and resulting canonical genome identity.

The v1 implementation bounds one in-memory run to 1,000,000 candidates. This is a resource limit, not a change to descendant identity; larger searches can be divided into explicit index ranges.

## Serial, parallel and ordering semantics

Workers claim explicit candidate indices independently. Each worker performs mutation, render, pixel hashing and descriptor calculation for only that address. Results are collected into index-addressed slots and emitted in strictly increasing descendant-index order.

Consequences:

- `--threads 1` and `--threads N` produce the same semantic batch manifest;
- task completion order cannot become candidate order;
- descriptor clustering and diversity selection always consume the same canonical index order;
- thread count is intentionally absent from candidate identity and the persisted semantic manifest.

## Render modes

### Canonical

`canonical` mode renders each descendant against the normalized full-resolution source through `render_pipeline_at_frame`. The stored pixel identity is the same content-based canonical RGBA8 identity used by the existing renderer/session tests. For the same source/genome/frame it must agree exactly with GUI/session canonical output.

### Proxy

`proxy` mode first creates the accepted deterministic FM-004 nearest-neighbour proxy from the full source identity and explicit `ProxySpec`, then renders the exact descendant genome against that proxy. The batch manifest records the render mode and proxy method/bounds.

Proxy mining is an explicitly non-full-resolution search aid. Selected contact sheets and optional selected stills still use the FM-012 canonical export service against the full normalized source.

## Visual descriptor v1

Descriptor version `1` is an exact 24-component unsigned-integer vector. All components use deterministic integer arithmetic and are normalized to `0..65535` where applicable. No floating-point colour conversion, display profile, GPU result or unordered reduction participates.

Components, in order:

1. four luminance-histogram bins;
2. sixteen spatial luminance means over a fixed 4x4 destination grid;
3. mean absolute horizontal luminance edge magnitude;
4. mean absolute vertical luminance edge magnitude;
5. high-luminance occupancy (`Y >= 128`);
6. equal-adjacent-row-mean occupancy.

Canonical integer luminance reuses the FM-007 coefficient rule:

```text
Y = (54*R + 183*G + 19*B + 128) >> 8
```

Spatial cells use `cell_x = floor(x*4/width)` and `cell_y = floor(y*4/height)`, each clamped to `0..3`. Empty cells are zero. Mean byte-domain quantities are integer-rounded by adding half the positive denominator before division, then mapped to `0..65535` by multiplying the `0..255` result by 257.

Histogram/occupancy quantities are integer round-to-nearest fractions of 65535. The test suite freezes a 2x2 known-answer descriptor vector.

## Descriptor distance and threshold

Descriptor distance v1 is the unsigned L1/Manhattan sum across all 24 components:

```text
distance(A,B) = sum(abs(A[i] - B[i]))
```

Only descriptors with the exact supported version and dimensionality are comparable. Near-duplicate threshold comparison is **inclusive**: `distance <= threshold` joins the candidate to the first eligible prior representative. Tests freeze the exact threshold-boundary behaviour.

This metric measures deterministic visual similarity features only. It is not a perceptual-quality or aesthetic score.

## Exact and near-duplicate policy

Classification is deterministic and performed in increasing descendant-index order.

Each successful candidate records three representative indices:

- `genome_representative_index` — first candidate with exactly the same canonical genome identity;
- `pixel_representative_index` — first candidate with exactly the same rendered pixel identity;
- `near_representative_index` — first exact-pixel representative whose descriptor is within the inclusive near threshold.

These distinctions are deliberately retained. Different genomes may converge to identical pixels, for example when a mutation changes a disabled operator. Such candidates remain distinct at genome/provenance level while sharing one pixel representative. Same-genome and same-pixel are never silently conflated in the manifest.

Near-duplicate grouping is applied only to exact-pixel representatives. The first representative wins deterministically; no clustering library, randomized initialization or worker-order-dependent merge is used.

## Diversity/novelty selection v1

Selection operates only on near-duplicate representatives and does not claim subjective quality.

The v1 procedure is deterministic farthest-point sampling:

1. choose the earliest eligible descendant index as the first selected specimen;
2. for every remaining eligible candidate, compute its minimum descriptor distance to the selected set;
3. choose the candidate maximizing that minimum distance;
4. break equal-distance ties by lower descendant index, then lexicographically lower genome identity;
5. repeat until the requested count or eligible set is exhausted.

The stored `novelty_distance` is the minimum descriptor distance at the time the candidate entered the selected set; the first candidate uses zero because it has no prior selected reference.

This is explicitly a diversity/coverage heuristic, not an aesthetic-quality metric.

## Batch manifest v1

`batch.fmbatch.json` is strict UTF-8 JSON with one final LF. It records:

- manifest, descriptor and mutation-policy versions;
- source identity;
- parent genome identity and complete canonical parent genome text;
- explicit mutation seed/radius/index range/frame;
- render mode and proxy specification;
- near-duplicate threshold and requested selection count;
- complete/cancelled state;
- every successfully completed candidate in index order;
- structured failed candidate indices/messages.

Each candidate records:

- descendant index and candidate identity;
- canonical genome identity and complete canonical genome text;
- rendered pixel identity;
- complete descriptor vector;
- exact-genome, exact-pixel and near-duplicate representative indices;
- selection flag and novelty distance.

Candidate mutation provenance is reconstructed exactly from the manifest's parent identity/policy/seed/radius plus candidate index and is restored by the parser. The parser rejects unsupported versions, missing/unknown schema-owned fields, invalid identities, invalid canonical genomes, identity mismatches, bad descriptor shape/components, duplicate/out-of-order candidate indices and candidate-address identity mismatches.

Thread count, elapsed time and cache-hit counts are deliberately not serialized into the semantic manifest because they would make equivalent serial/resumed runs byte-different. The CLI reports these operational statistics separately.

## Resume/restart contract

`--resume` never trusts a filename or manifest record by itself.

A previous batch manifest must match the current source identity, complete parent genome, seed/radius/range/frame, render mode/proxy specification, near-duplicate threshold and requested selection count. A mismatched manifest is rejected rather than silently mixed into a new run.

For each potentially reusable candidate, the CLI decodes the deterministic candidate PNG cache and requires its normalized pixel identity to match the manifest. The core then independently:

1. regenerates the indexed descendant genome from the current authoritative parent/policy/address;
2. requires exact genome content/identity equality;
3. validates the cached canonical image dimensions and pixel identity;
4. recomputes descriptor v1 and requires exact vector equality;
5. recomputes and checks candidate identity.

Only then is the render reused. Any missing/stale/mismatched candidate cache is regenerated. The final semantic manifest and selected set therefore match an uninterrupted run.

## Output layout and GUI import

The headless tool writes deterministic outputs under the requested directory:

```text
batch.fmbatch.json             strict semantic batch manifest
batch.fmproj                   ordinary GUI-openable project v2
candidates/
  candidate_<20-digit-index>.png
selected-contact-sheet.png     FM-012 canonical selected contact sheet (unless disabled)
selected-contact-sheet.png.json
selected/                      optional canonical full-resolution selected stills/manifests
```

Candidate cache PNGs are deterministic-address working artefacts used for safe resume. Encoded PNG container bytes are not a canonical identity; decoded normalized pixels are.

`batch.fmproj` is produced through the existing `SessionModel`/project-v2 path. Selected mined specimens are retained as ordinary FM-010 mutation lineage nodes with exact FM-009 provenance and durable favourite state. A normal GUI project open can therefore continue exploration without inventing a separate batch-only specimen format.

Selected contact sheets and optional stills are produced through the existing FM-012 export service. They retain the existing export/provenance semantics instead of creating a second capture implementation.

## Source/project input

The CLI accepts either:

- `--source <image> --genome <genome.json>`, or
- `--project <project.fmproj>` with an optional explicit identical-content `--source` relink.

Project mode preserves current mutation locks. Ordinary project sources must pass the existing normalized source-identity check. FM-013 projects with embedded frozen laboratory pixels can be mined directly without re-running the external decoder.

## Cancellation and failures

Ctrl+C / Ctrl+Break requests cancellation. Workers stop claiming new indices; already completed candidates remain valid. The tool writes the completed candidate caches plus a strict manifest with `complete=false` and `cancelled=true` and returns a distinct cancellation exit code.

A candidate mutation/render/descriptor engineering failure is recorded with its explicit descendant index and message. A batch containing such failures is partial rather than silently pretending success.

Output commits use adjacent temporary files and Windows replace/write-through when the tool owns the output. A stale cached candidate is never accepted merely because its expected filename exists.

## CLI surface

Minimum invocation:

```powershell
.\build\Release\FAULTMINE-batch.exe `
  --source input.png `
  --genome genome.json `
  --out .\mine-001 `
  --seed 0123456789abcdef `
  --count 2048 `
  --threads 8
```

Useful options include explicit `--begin`, mutation `--radius`, semantic `--frame`, `--render canonical|proxy`, proxy bounds, inclusive `--near-threshold`, `--select`, `--resume`, `--selected-stills`, and `--no-contact-sheet`.

The tool prints both human-readable counters and a compact machine-readable JSON summary covering requested/completed/reused/failed candidates, exact unique genome/pixel counts, near-duplicate groups, selected count and complete/cancelled state.

## Verification contract

`deterministic_batch_mining_contracts` freezes at least:

- descriptor v1 known-answer values and identity distance;
- serial versus multi-thread semantic-manifest equality;
- strict batch-manifest canonical round trip and unknown-field rejection;
- verified full resume producing the same final semantic manifest as uninterrupted execution;
- stale cached pixels being rejected and regenerated;
- distinct-genome/same-pixel dedupe semantics;
- inclusive near-duplicate threshold boundary;
- deterministic diversity selection;
- canonical headless versus `SessionModel`/GUI render-byte/hash agreement;
- retention of selected mined specimens as normal project-v2 mutation lineage provenance;
- coherent strict partial manifests under cancellation.

All earlier deterministic suites and the native Debug/Release Win32/D3D smoke remain required. Changing descriptor components/order/rounding, distance, candidate identity, dedupe order or selection/tie-breaking is a versioned contract change rather than a fixture-only update.
